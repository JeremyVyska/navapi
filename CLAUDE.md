# navapi — agent notes

Discovery-first toolkit for Microsoft Dynamics 365 Business Central APIs. pnpm monorepo, four packages: `packages/core` (`@navapi/core` — the brain), `packages/cli` (`@navapi/cli`, installs the `navapi` command), `packages/mcp` (`@navapi/mcp`), `packages/vscode` (`navapi-vscode` extension, ships as `.vsix`).

**Design rule:** anything not UI-specific goes in `core`. The faces stay thin and all resolve profiles/secrets through `createClientForProfile()` / `resolveSecretStore()`.

## Commands

```bash
pnpm build            # tsup, all packages
pnpm test             # vitest, all packages (~130 tests)
pnpm lint / lint:fix  # biome (formatter is strict; LF enforced via .gitattributes)
pnpm --filter navapi-vscode package   # builds the .vsix (bump the version FIRST — see below)
cd packages/vscode && npx tsc --noEmit  # only package that needs a manual typecheck
```

## Non-obvious rules (each learned the hard way)

- **BC string fields are present-but-empty**, never rely on `??` for fallbacks. Use `companyLabel()` from core.
- **`$top` never yields `@odata.nextLink`.** Paging = `Prefer: odata.maxpagesize` (`ListOptions.maxPageSize`). `$top` is only a hard cap.
- **Route enumeration is company-scoped**: runtime API `GET <env>/api/microsoft/runtime/beta/companies(<id>)/apiRoutes` (then v1.0, then bare `api/routes`, then plain `v2.0`). No company → only standard routes appear.
- **ETag pattern:** GET → `If-Match` → retry once on 412 → surface. Lives in core only.
- **Credentials and targets are separate things.** A `Credential` (`{name, type:'clientSecret', clientId}` | `{name, type:'azureCli', account?}`) is an identity; a `TargetContext` (`tenantId`, `environment`, `company?`, `baseUrl?`) is where a request goes; a `ProfileConfig` is a saved name for one pointed at the other, via `credential: <name>`. One credential can back many profiles — that's the point, and it's why **secrets are keyed by credential name, not profile name**. `profiles.json` is `{version:2, credentials:{}, profiles:{}}`.
- **Three on-disk shapes, one read path.** v0 (published 0.2.0) put `clientId` at the top level of a profile; v1 (merged after 0.2.0 but **never published**) used an `auth` discriminated union; v2 is the credential ref. `migrate()` in `profiles.ts` converts v0/v1 **in memory on read** and the file is only rewritten when something changes it — a plain read must never migrate the file, or an older navapi can no longer read it. Migration mints **one credential per profile, named after the profile**, deliberately *not* deduplicating by client ID: two profiles on the same app registration may have different secrets stored under their own names, and merging would authenticate one with the other's secret. Naming them after the profile also means a migrated setup needs **no keychain writes** — the secret is already under the right key. `serializeProfile()` still writes the legacy top-level `clientId`, so a downgrade to the published 0.2.0 keeps working. `ProfileStore.upsert()` accepts the v0/v1 literal too (external embedders and the MCP tests build it) and mints a credential the same way.
- **One resolution rule, in core.** `createClientForSelector()` in `factory.ts` is what every face calls. With no overrides: named profile → `NAVAPI_PROFILE` → stored default. Naming any of credential/tenant/environment layers *over* the profile rather than replacing it, so `navapi get customers --tenant <other>` reuses the profile's credential and environment — the cross-tenant case that used to need a saved profile per tenant. `createClientForProfile()` and `createClientForTarget()` are the two ends it dispatches to. An overridden target must **not** reuse the profile's name, or ad-hoc calls pollute a saved profile's metadata cache (`targetLabel()` gives them their own).
- **The target flags are per-command, never global.** `profile add` and `credential add` declare their own `--tenant`/`--environment`/`--credential`; a root-level flag of the same name shadows the subcommand's and silently breaks `profile add`. `program.ts` walks the command tree **recursively** (`braider config ls` is two levels down) and adds them to every leaf outside the config groups. `test/program.test.ts` pins this — it only fails when the CLI actually parses.
- **Two auth strategies, one branch point.** `Credential` is a discriminated union so a new method adds a variant instead of more optional fields. `createAuth()` in `factory.ts` is the only place that branches — that's why az-cli auth works in the CLI, MCP, and VS Code with no changes to any of them. The az-cli path must skip secret resolution entirely, or it fails on a missing secret that was never needed. `AzureCliAuth` shells out to `az account get-access-token -o json` (`-o tsv` has no expiry, which would cost a subprocess per request); it takes an injectable `exec` so tests never spawn anything, and validates tenant/resource against a strict charset because Windows needs `shell: true` to run `az.cmd`.
- **az picks the identity from its active account, not from `--tenant`.** Cross-tenant works whenever an identity az holds has access (GDAP, guest, or a native account) — otherwise you get AADSTS50020, which means "wrong identity", not "wrong tenant". A credential's `account` pins an **identity** (not a tenant's account — the same identity often reaches tenants az holds no account in). Resolution order in `resolveAccountSelector()`: an account for that identity **in the profile's tenant** → `--subscription <id>`; otherwise, if the identity is az's *active* account → `--tenant <id>`, which is the only way to express GDAP/guest access; otherwise refuse, because `--tenant` would silently authenticate as whoever is active. `--subscription` and `--tenant` are mutually exclusive in az, and `--subscription` does *not* change az's global active account. The id passed on the command line always comes from az's own output, never from user input. UI layers (CLI picker, `profile az-accounts`, the VS Code dropdown) collapse `listAzureCliAccounts()` by username and mark the active one — listing per tenant implies a binding that doesn't exist.
- **`@napi-rs/keyring` must stay in tsup `external`** (core AND vscode configs) — esbuild chokes on `.node` files. The vsix gets it via `packages/vscode/scripts/copy-keyring.mjs` → `dist/node_modules` (single-platform: host's binding only).
- **Always bump `packages/vscode/package.json` version before packaging a vsix** — VS Code silently keeps stale same-version installs. The records panel shows `v<version>` in its toolbar to diagnose this.
- **Extension exposes MCP to Copilot:** the vsix bundles a second tsup entry `src/mcp-server.ts` → `dist/mcp-server.mjs` (ESM; `@navapi/mcp` + SDK + `zod` are devDeps of the vscode pkg so esbuild can bundle them; keyring stays external). `activate()` registers it via `vscode.lm.registerMcpServerDefinitionProvider('navapi.mcp', …)` returning an `McpStdioServerDefinition(label, process.execPath, [dist/mcp-server.mjs], mcpServerEnv(profile, configDir), version)` — needs `contributes.mcpServerDefinitionProviders` in package.json, `engines.vscode ^1.101.0`, and `!dist/mcp-server.mjs` allowlisted in `.vscodeignore`. The env sets `ELECTRON_RUN_AS_NODE=1` so the editor binary runs the script as node; profile switches fire the provider's change event. Pure env logic is in `src/mcp-config.ts` (unit-tested); the bundled server is smoke-tested standalone (scratchpad `mcp-smoke.mjs` pointed at `dist/mcp-server.mjs`).
- **Webviews:** toggle CSS classes, never `style.display = ''` (stylesheet default wins). All grid/filter logic is pure TS (`grid.ts`, `filter.ts`, `webview.ts`) tested in jsdom (`test/webview-dom.test.ts` executes the real embedded script). Record data is rendered DOM-only (XSS).
- **fast-xml-parser:** with `attributeNamePrefix: ''`, the `isArray` callback must check its `isAttribute` argument or attribute names collide with element names.
- **Exports never carry secrets, and imports refuse files that do.** `portability.ts` is the whole format (`PORTABLE_VERSION`, versioned independently of any package). `buildPortableConfig()` exports only the credentials the exported profiles reference, and strips an azureCli credential's `account` — it pins *one person's* login and is wrong on any other machine. `parsePortableConfig()` rejects a document containing `clientSecret`/`secret`/`password` rather than dropping the field, because navapi never writes one: its presence means that secret was already mishandled. `planImport()` decides everything before anything is written, so a run either applies cleanly or reports every collision at once.
- **Secrets:** never write to the real keychain from tests/smokes — set `NAVAPI_SECRET_BACKEND=file` (CI does; smoke scripts do).
- **CLI `--json` output shape is a stability promise** — bare arrays/objects by default; envelopes only behind opt-in flags (e.g. `--count`).
- **Data Braider payloads are double-encoded** (stringified JSON inside `jsonResult`/`filterJson`/`jsonInput`); the unwrap lives ONLY in `core/src/braider.ts` (`parseJsonResult`/`encodeJsonInput`/`encodeFilterJson`). Braider errors arrive as `[{Row, Column, Error, Detail}]` arrays *inside* jsonResult, not as HTTP errors.
- **Braider `pageStart` is a 1-based PAGE INDEX** (skip = `(pageStart−1)×pageSize` top-level records) and requesting past the end is a server-side error — the `all` loop is bounded by `topLevelRecordCount`, never probe-until-empty. Deliberately NOT named/typed like `maxPageSize` (different semantics).
- **Braider enum values are EDM-encoded on the wire** (`Per_x0020_Record`); `decodeODataName`/`encodeODataName` handle both directions. Config-API entity-set names live in exactly one place: `resolveConfigSets()` in braider.ts.
- **Braider capability levels:** level 1 = `read`+`write` only (schema falls back to inference from sampled rows); level 2 (Braider 2.4+) adds `endpointConfigs`/`endpointLines`/`endpointFields`/`endpointRelations`/`endpointSchemas`/`availableTables`/`availableFields`. Config methods throw a clear NavApiError at level 1 — keep that graceful degradation intact.

## Release

**Marketplace vsixes:** `pnpm --filter navapi-vscode package:all` (`scripts/package-all.mjs`) builds one vsix per VS Code target under `dist/vsix/`, each bundling only that platform's `@napi-rs/keyring` binding (downloaded from npm via `npm install --prefix`, not the flaky host `tar`). The plain `package` script is still host-binding-only for local dev. `package:universal` (`… universal`) instead builds ONE universal vsix bundling all bindings (~7MB) — the loader still picks the right one at runtime. Gotchas baked in: Marketplace rejects SVG as the extension `icon` (use `media/icon.png`, regenerated by `scripts/make-icon.mjs` from the compass SVG — no image tooling needed); `CHANGELOG.md` must be `!`-allowlisted in `.vscodeignore` or it won't ship; vsce lowercases readme/changelog/license inside the vsix. Publisher is `jeremyvyska` (no hyphen — baked into every manifest at package time). **The user publishes by uploading the vsix through the Marketplace web UI** (`marketplace.visualstudio.com/manage/publishers/jeremyvyska`), NOT `vsce publish` — see `docs/releasing.md` for why that is a considered decision, not a gap. The universal vsix is the single-file artifact for that upload.

**Releases are tag-triggered** — see `docs/releasing.md`, which is the authority. `.github/workflows/release.yml` verifies (incl. that the tag matches every package version — a mismatch publishes the wrong version irrecoverably), publishes the four public packages to npm, builds the universal vsix, and drafts a GitHub Release with it attached. npm uses **trusted publishing (OIDC)**: no `NPM_TOKEN`, no OTP, so the old "needs a REAL interactive terminal" constraint is gone. npm trusts the repo + **this workflow filename**, so renaming `release.yml` breaks publishing until npmjs.com is updated; the publish job must stay on Node 22+ and a GitHub-hosted runner. pnpm does the exchange itself and **11.0.8 is broken (404)** — the root `packageManager` pin is load-bearing. A never-published package can't have a trusted publisher configured (nothing to configure it on), so its first publish is manual. The Marketplace upload stays manual: `vsce` needs a *global* Azure DevOps PAT, Microsoft retires those 2026-12-01, org-scoped support is unconfirmed (vsmarketplace#2121, open), and the Entra replacement is documented only for ADO Pipelines. The web upload uses a browser session and is unaffected. The bare `navapi` npm name is squatted (CLI is `@navapi/cli`, bin is still `navapi`). All packages are at **0.3.0** (lockstep — the vsix bundling assumes it) with publishConfig `tag: latest`. GitHub Releases: `v0.1.0-alpha.1` was the old prerelease, `v0.2.0` shipped 2026-07-05; `v0.3.0` is the current wave and the first cut by the workflow rather than by hand. CI: `.github/workflows/ci.yml` (ubuntu/windows × node 20/22; pnpm needs `standalone: true` because pnpm 11 requires Node ≥22.13).
